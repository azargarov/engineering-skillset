# Engineering Skillset v0.3 — M01 Architecture & Contracts Proposal

**Status:** Superseded by the Skill-based model delegation direction recorded
in [`../../ROADMAP.md`](../../ROADMAP.md). Retained unchanged as historical
proposal; the accepted declarative routing architecture and M02 plan are no
longer the active v0.3 scope.
**Baseline:** Published v0.2.1. Approved architecture: Option A, declarative
routing with manual execution.
**Scope:** Finalize M01 and prepare a bounded M02 plan. No executor invocation,
provider API calls, implementation, preset changes, or Skill changes.

## 1. Existing architecture and constraints

The product's authoritative intent is [`../../VISION.md`](../../VISION.md).
Four named presets select policy levels/priorities and compile through Make
into standalone `dist/<preset>/AGENTS.md` and Skills. `software-design` and
`verification-qa` have preset variants; `implementation-review` and
`project-handover` are shared Skills. A preset is engineering strategy, not a
provider selection.

`ess` supports `list`, `install`, `status`, and `uninstall`. It installs a
copied `AGENTS.md` and links Skills to the active distribution. The user
installer publishes immutable releases containing the four preset outputs and
the `ess` runtime, then updates the stable `current` link. Installation
ownership state and compatibility behavior are independent of this proposal.
There is no task execution, executor config, or contract handling in the
current CLI.

Core Policy requires authorized scope, preservation of contracts, proportionate
verification, truthful evidence, and project-memory continuity. The QA Skill
requires review → final verification → acceptance reporting. Project handover
distinguishes development history, current state, and backlog. Keep those as
shared authorities referenced by a task contract, not copies embedded in each
contract.

No project ADRs were found. `decisions/` files under evaluation fixtures are
test inputs, not project architecture decisions. Existing architecture
decisions to preserve include explicit Make selections, standalone generated
artifacts, `ess` installation from built outputs, stable install layout, and
separation of policy modules from workflow Skills. The published v0.2.1
installer/preset behavior remains the compatibility baseline.

## 2. Approved routing model

Keep routing declarative and advisory. Configuration identifies executor
profiles and ordered rules. It does not install, authenticate, launch, or prove
an executor is safe. The operator launches the chosen tool manually.

### Configuration location and format

Use strict, versioned JSON: it is human-readable, has a standard syntax, and
can be consumed later without requiring a YAML dependency. The per-user file
is `${XDG_CONFIG_HOME:-~/.config}/engineering-skillset/routing.json`.
No secret belongs in it. Project-local overrides are deferred; they raise
trust, precedence, and data-disclosure questions that are not necessary for a
manual first version.

The configuration below illustrates the approved format. Provider and model
identifiers are examples, not a supported compatibility list. Capability
declarations are assumptions until qualified for a specific runner/provider/
model version.

```json
{
  "schema_version": 1,
  "default_executor": "codex-local",
  "executors": {
    "codex-local": {
      "runner": "codex",
      "provider": "openai",
      "model": "codex-default",
      "location": "local",
      "capabilities": ["read", "write", "shell", "coding"]
    },
    "opencode-deepseek": {
      "runner": "opencode",
      "provider": "deepseek",
      "model": "deepseek-v4-pro",
      "location": "cloud",
      "capabilities": ["read", "write", "shell", "coding"]
    },
    "ollama-review": {
      "runner": "opencode",
      "provider": "ollama",
      "model": "qwen3-coder",
      "location": "local",
      "capabilities": ["read", "review"]
    }
  },
  "routes": [
    {
      "category": "code-change",
      "location": "local",
      "executor": "ollama-review",
      "fallbacks": ["codex-local"]
    },
    {
      "category": "code-change",
      "location": "local",
      "executor": "codex-local",
      "fallbacks": ["opencode-deepseek"]
    }
  ]
}
```

`runner` identifies the tool/harness the operator will invoke; `provider` and
`model` identify the configured inference endpoint/model as known to that
runner. `capabilities` are explicit declarations for routing, not verified
guarantees. `location` is the basic local/cloud preference. Do not infer that
an API's function-calling feature grants filesystem, shell, or autonomous
coding capability.

### Routing, precedence, and validation rules

- Parse strict JSON and reject unknown schema versions, unknown properties,
  duplicate executor IDs/capabilities, malformed IDs, invalid locations,
  empty required strings, and references to missing executors.
- Task requirements are authoritative: category, required capabilities, and
  locality determine compatibility. Config rules may narrow candidates but
  cannot weaken or replace task requirements.
- Evaluate routes in declared order. A route is applicable when its category
  matches and any locality selector matches. For each applicable route, test
  that route's executor against every task-required capability and locality.
  Select the first compatible executor. If a candidate fails, report the
  missing capabilities or locality mismatch and continue to later applicable
  rules. A compatible executor in a later rule may therefore be selected.
- After all applicable routes, test `default_executor` as the final ordinary
  candidate. It must satisfy all task requirements. A default never bypasses
  capabilities or locality. If no compatible candidate remains, return an
  explainable no-match result with each candidate failure.
- Example: a `code-change`/`local` rule points to an executor declaring only
  `read`; a later matching `code-change`/`local` rule points to one declaring
  `coding` and `write`. For a task requiring both, skip the first with reason
  “missing coding, write” and select the second. If the default is cloud-only
  while the task requires local, reject it and report the locality mismatch.
- Rules are first-compatible, not first-applicable. Their order determines
  preference among compatible candidates and is visible in the preview.
  Invalid categories, locations, or executor references fail config
  validation rather than silently becoming non-matches.
- Fallbacks are ordered manual recommendations, never automatic execution.
  After selecting an executor, check its configured fallback list in order
  against the same task requirements; report only compatible candidates and
  why each qualifies. On no match, check recommendations from applicable
  rules in declared order and explain why incompatible ones were omitted.
  Fallbacks cannot override category, capability, or locality requirements.
- A route preview does not test whether a runner is installed, authenticated,
  online, or actually grants the declared tools. It reports configured
  compatibility only; availability and effective permissions are operator
  preflight facts.
- Static validation checks syntax and internal references. Availability is a
  separate manual/runtime fact: before launch, the operator confirms the
  runner is installed, authenticated, points to the intended model, and is
  configured with appropriate tools/permissions. A failed availability check
  stops that recommendation and offers only compatible configured fallback
  recommendations.
- An explicit executor override is permitted only if that executor satisfies
  every mandatory task requirement. Reject an incompatible override in the
  MVP and report missing capabilities/locality. Experimental incompatible
  execution is deferred to a future design. A compatible override is recorded
  in the contract with its rationale. No executor is launched by routing.

This is intentionally a small declarative selector, not a model ranking,
plugin system, package manager, capability discovery protocol, or security
boundary.

## 3. Task Contract

Represent a manual task as a compact JSON document. The contract is the
handoff brief for the executor and the checklist for review. Inputs should
prefer paths, commit IDs, issue references, or short excerpts over copying an
entire repository policy or memory file.

### Mandatory fields

`contract_version`, `objective`, `category`, `required_capabilities`, `scope`,
`deliverables`, `acceptance_criteria`, `required_verification`, and `executor`
are mandatory. `inputs` and `constraints` are optional arrays and may be empty
or omitted when there are none. Objective, authorized scope, deliverables,
acceptance criteria, and verification requirements must be meaningful for
the task. `executor.id` identifies the selected executor (or compatible
override); `executor.reason` records the route or override rationale.

### Optional fields

`context_refs` can point to project instructions, relevant architecture,
roadmap/current records, or prior evidence. `excluded_scope` clarifies likely
scope confusion. `risk`, `location_preference`, and `notes` add task-specific
detail only where useful. Contract ID, creation time, and expiry can be added
when a durable run record is needed; they are not required to start manual
execution.

```json
{
  "contract_version": 1,
  "objective": "Add a request ID to the health endpoint response.",
  "category": "code-change",
  "required_capabilities": ["coding", "write"],
  "inputs": [
    "src/health.py",
    "tests/test_health.py",
    "User request in issue ENG-142"
  ],
  "context_refs": [
    "AGENTS.md",
    "docs/api-contract.md"
  ],
  "scope": {
    "allowed": ["src/health.py", "tests/test_health.py"],
    "excluded": ["database schema", "deployment configuration"]
  },
  "constraints": [
    "Keep the existing response fields and status code.",
    "Do not add dependencies."
  ],
  "deliverables": [
    "Updated health response implementation",
    "Focused regression test"
  ],
  "acceptance_criteria": [
    "A successful response includes a non-empty request_id.",
    "Existing response fields and status code remain unchanged."
  ],
  "required_verification": [
    "Run the focused health endpoint tests.",
    "Report exact command and result; identify unrun checks."
  ],
  "executor": {
    "id": "codex-local",
    "reason": "First matching code-change route; declares coding and write."
  },
  "risk": "low"
}
```

The JSON shape above is an example contract, not a released schema. A
validator should reject missing mandatory fields, empty objective or
authorized scope, unknown categories/capabilities, empty deliverables,
acceptance criteria, or verification requirements, malformed references, and
invalid executor IDs. Empty or omitted `inputs` and `constraints` are valid.
The validator checks `required_capabilities` against the selected executor;
it does not infer whether natural-language criteria are complete. That remains
a human/agent review step.

Contracts should normally be ephemeral: kept in the conversation or an
operator-selected scratch location, not automatically committed. If task
history affects project continuity, record the meaningful outcome in the
existing milestone/decision/current records and link to a retained contract or
report only when useful. Do not duplicate long-lived project memory in each
task contract.

## 4. Manual execution workflow

1. The user or agent describes the objective, scope, constraints, deliverables,
   acceptance criteria, and required verification. Missing material
   authorization or acceptance details are clarified before execution.
2. Read and statically validate the routing config. Match category, required
   capabilities, and optional local/cloud preference using first-match rule
   order. Report the selected executor and matching rule; if there is no
   compatible selection, stop and explain the gap.
3. Prepare the task contract with context references rather than copies of
   Core Policy or project memory. Record any explicit override and rationale.
4. The operator checks runner/model availability, credentials, and tool
   permissions, then launches the executor manually. For code changes, use an
   operator-chosen isolated checkout/worktree when available and preserve the
   primary checkout until review. M01 does not provide or enforce a sandbox.
5. The executor returns artifacts or a patch plus a report mapping changes,
   commands/checks, results, and limitations to the contract. The operator
   inspects the actual diff and evidence; executor assertions alone do not
   establish acceptance.
6. Apply the project's existing implementation review, final QA, and
   acceptance gates. The operator decides whether to integrate the work.
   Update project memory with verified meaningful outcomes, decisions,
   blockers, and next steps according to the current Core Policy.

Unsupported capability: do not route to that executor as a compatible match.
Recommend configured compatible alternatives or ask the operator to revise
task requirements. An explicit incompatible override is rejected in the MVP.
Unavailable runner/model/authentication cannot be determined by route preview;
the operator checks availability before manual launch. Do not silently switch
or invoke a fallback.

## 5. Product integration and compatibility

- **`ess`:** add a read-only `route` subcommand in M02. It belongs in the
  existing CLI because routing is an Engineering Skillset operation and the
  current command is a small Bash dispatcher. A separate tool would duplicate
  entry points and configuration lookup. Keep the addition isolated from
  install/switch/status/uninstall semantics. The precise helper/runtime
  packaging plan is in the M02 plan below.
- **Configuration ownership:** proposed per-user routing config lives outside
  the project and outside the published distribution. It can contain model
  identifiers but no credentials. Project-local routing config and precedence
  are deferred pending an approval decision.
- **Distribution:** M01 adds only architecture/schema/example documentation to
  the source repository. No routing config, executable, contract template, or
  new runtime file is added to `dist/<preset>`, immutable user releases, or
  project installations. Existing compiled AGENTS and Skill paths remain
  unchanged.
- **Presets:** the four presets continue to control engineering approach and
  QA rigor. Routes may use task category/capability, but do not alter or encode
  a preset's verification requirements. The selected preset/project policy
  informs the contract's required checks.
- **Future automated execution:** a later runner could consume the same
  versioned contract and executor ID, validate it, then return status,
  artifacts, and evidence. Manual and automated paths must share scope,
  acceptance, and QA fields. Automation would require a separately approved
  runtime, isolation, timeout, credential, cancellation, and trace design.

## 6. Design decisions and trade-offs

| Decision | Rationale | Cost / unresolved point |
|---|---|---|
| Strict versioned JSON in per-user XDG config | Standard parse format; no provider secrets or project-level config | Less comment-friendly than YAML; route command requires a JSON parser |
| First compatible executor in declared rule order | Easy to inspect, test, and explain; candidate failures remain visible | Ordering affects preference; preview should explain skipped candidates |
| Default is the final compatibility-checked candidate | A default cannot bypass task requirements | May produce a no-match requiring operator action |
| Fallbacks are suggestions, never automatic | Preserves manual execution and identity/permission awareness | Less convenient during provider outages |
| Provider/model separate from runner | A model API is not an executor; same harness can target different endpoints | Model capability declarations require qualification and can become stale |
| User-level config only for initial version | Avoids untrusted repository config changing provider choice or disclosure | Shared team routing and project-specific defaults are deferred |
| Task contracts are ephemeral by default | Avoids unnecessary repository artifacts and memory duplication | Repeatability needs an operator-selected saved copy when needed |
| Read-only `ess route` preview, no execution | Gives deterministic route rationale using the existing CLI; does not alter installation commands/state | Adds one helper and a Python 3 requirement for `ess route` only |

No ADR is created because the repository has no established ADR convention.
M01 acceptance is recorded in this architecture document and project roadmap.

### Configuration schema v1

Strict JSON top-level object:

| Field | Type/rule |
|---|---|
| `schema_version` | Required integer `1`. |
| `default_executor` | Required configured executor ID; evaluated after explicit route candidates and checked against all task requirements. |
| `executors` | Required non-empty object keyed by unique IDs. Each entry has required non-empty `runner`, `provider`, `model`, `location` (`local` or `cloud`), and unique `capabilities`. |
| `routes` | Required ordered array. Each rule has `category`, `executor`, optional `location`, and optional ordered `fallbacks`. Reject unknown keys, invalid vocabulary, duplicate fallback IDs, dangling references, and malformed values. |

Proposed category vocabulary: `analysis`, `review`, `documentation`,
`code-change`, and `verification`. Proposed capability vocabulary:
`read`, `write`, `shell`, `coding`, and `review`. These are simple labels;
`coding` remains distinct from `write` so a task may require both model coding
behavior and edit capability. Capability declarations are assumptions until
qualified. Do not infer them from provider/model names. Credentials, project
configuration, schema migration, capability discovery, and API calls are
excluded.

Resolve config from
`${XDG_CONFIG_HOME:-$HOME/.config}/engineering-skillset/routing.json`.
`XDG_CONFIG_HOME` must be absolute. If the config is absent, report the exact
expected path; do not synthesize a default. Check that it is a readable regular
file. Reject duplicate JSON object keys and non-standard constants in addition
to syntax errors. Unknown versions/keys, invalid IDs, empty required values,
invalid categories/capabilities/locality, duplicate IDs/capabilities, and
unresolved references are configuration errors. Never echo credential-like
values in diagnostics.

### Task-contract schema v1

The contract remains a manual handoff format. M02 does not add contract
creation, persistence, or a contract subcommand.

Required fields: `contract_version` integer `1`; non-empty `objective`;
recognized `category`; `required_capabilities` array; `scope` object with a
non-empty `allowed` array and optional `excluded` array; non-empty
`deliverables`, `acceptance_criteria`, and `required_verification` arrays; and
`executor` with a configured `id` plus non-empty routing `reason`. Optional
`inputs` and `constraints` arrays may be omitted or empty. Optional
`context_refs`, `risk`, `location_preference`, and `notes` are task-specific.
Natural-language adequacy remains subject to human review. Do not include a
copy of Core Policy or project-memory contents.

The route command consumes selectors, not a contract file. Contract authoring
and runtime contract validation are deferred until a user-facing contract
workflow is authorized. M02 will parse and check the realistic contract
example as a documentation fixture for strict JSON and required/optional field
presence, preventing the example from drifting from this specification.

### CLI interface, routing algorithm, and output

```text
ess route --category code-change --requires coding,write
ess route --category review --requires review,read --locality local
ess route --category code-change --requires coding,write --executor codex-local
```

Require exactly one category. `--requires` is a comma-separated list; an
omitted or empty value means no capability requirement. Reject empty elements,
duplicates, and unknown capability names. `--locality` accepts `local` or
`cloud`. `--executor` requests an explicit compatible override: require a
configured executor satisfying every capability and locality requirement.
Reject unknown or incompatible overrides and report why. A compatible
override supersedes route selection and is identified as an override in the
output. There is no force flag.

Without an override:

1. Visit routes in declaration order. Skip selector mismatches (category or
   route-locality mismatch).
2. For every applicable rule, test its executor's configured locality and
   declared capability set against the complete task requirement set. Record
   failures and continue. Select the first compatible executor.
3. If no explicit rule candidate is compatible, test `default_executor` once
   as the final candidate, under the same requirements.
4. If none is compatible, return no-match with all relevant skipped candidate
   reasons. Defaults and fallbacks never weaken task requirements.
5. Report compatible fallback recommendations from the selected rule. If
   selection fails, inspect fallback recommendations from applicable rules in
   declaration order. Filter using the same capability/locality requirements
   and deduplicate while preserving order. Never launch them.

Example: the first matching `code-change`/`local` rule refers to an executor
with only `read`, while the next matching rule refers to one with `coding` and
`write`. A request requiring `coding,write` skips the first rule with the
missing capability reason and selects the second. If the default is cloud-only
for a local task, it is rejected as a candidate. If there is no other
compatible candidate, output no-match and the locality reason. A fallback
lacking either required capability is omitted with its reason.

Output deterministic plain text containing task selectors, selected executor
or no-match, matching rule index/category (or `default`/`override`),
compatibility rationale, compatible fallback recommendations, and rejected
candidate reasons. State that runner installation/authentication/availability
and capability truth are not checked. The command does not launch executors,
make API calls, inspect credentials, or modify project files.

### Error handling and exit codes

- `0`: selected compatible executor; include compatible fallbacks, if any.
- `1`: valid request and config, but no compatible executor (including an
  incompatible explicit override). Print deterministic no-match reasons to
  stdout so scripts can inspect the result.
- `2`: usage/argument error, missing/unreadable config, malformed JSON,
  unsupported schema version, or invalid config. Print a concise explanation
  to stderr, following existing `ess` usage/configuration error conventions.
- Python 3 unavailable or helper missing from an old installed release: exit
  `2` with an actionable diagnostic. Existing commands remain Bash-only.

### Implementation sequence and focused verification

1. Freeze categories, capabilities, config path, and schema error semantics.
   Add valid/invalid routing JSON fixtures and the task-contract example
   fixture; check that empty/omitted inputs and constraints are accepted.
2. Implement strict JSON loading and routing-config validation in
   `scripts/ess_route.py` with Python standard library only. Reject duplicate
   keys using an object-pairs hook and reject non-standard constants. Add
   focused tests for malformed JSON, duplicate keys, unsupported versions,
   unknown keys, invalid values, duplicates, dangling references, and
   unreadable/missing config.
3. Implement a pure candidate evaluator and test: first-compatible precedence;
   first-applicable incompatible followed by compatible; default compatibility
   and rejection; capability subset; locality; no-match reasons; fallback
   filtering, ordering, and deduplication; compatible override; rejected
   incompatible/unknown override.
4. Add CLI argument handling and deterministic output. Test the documented
   invocations, malformed lists/flags, selected rule/rationale, recommendations,
   no-match output/status, config error output/status, and absence of any
   subprocess/provider call.
5. Wire `ess route` to the helper. Checkout mode uses the repository helper;
   installed mode resolves `current/ess_route.py`. Update `install-user.sh` to
   validate and copy the helper into the staged immutable release before
   activation. Preserve existing preset links and project ownership state.
   Add the unit-test command to the existing `make check` orchestration.
6. Extend installed CLI tests to confirm helper presence and stable-current
   resolution. Run focused tests and existing `make check`/installer lifecycle
   checks in disposable roots. Confirm all four preset outputs and user
   install/uninstall behavior match the v0.2.1 baseline; an absent route config
   must not affect existing commands. Review diff and run `git diff --check`.

Python 3 is required only for `ess route`; current commands stay Bash-only.
The repository already uses Python 3 in its build checks, but the installed CLI
has not previously required it. Confirm the minimum supported Python 3 version
before implementation. This is the main compatibility cost of using strict
standard-library JSON parsing instead of adding `jq` or embedding a fragile
parser in Bash.

### Required MVP and deferred features

**MVP:** per-user strict config; deterministic route preview; first-compatible
selection; compatibility-checked default and fallbacks; compatible explicit
override; explainable no-match; stable exit codes; installable helper; focused
schema/routing/CLI/installation tests.

**Deferred:** execution, subprocess/provider/API access, availability probes,
automatic fallback, incompatible override, project-level config, contract
creation/persistence/CLI validation, secrets, scoring, learned routing,
concurrency, worktree orchestration, database/service, and v0.4
effectiveness evaluation.

### M02 acceptance criteria

- Config is strictly validated before routing; no project config, secrets, or
  provider calls are involved.
- Preview selects the first compatible candidate under ordered rules, checks
  default last, explains candidate failures, and recommends only compatible
  fallbacks.
- Compatible override works; incompatible/unknown override fails with a
  reason.
- Contract v1 schema and mandatory/optional field rules are documented; its
  example is valid JSON and matches the field contract, including optional
  empty inputs/constraints.
- Output and exit codes are deterministic. The command never launches an
  executor or modifies project files.
- Checkout and installed CLI route preview work; existing v0.2.1 installation,
  preset, Skill, ownership-state, and lifecycle behavior remains unchanged.
- Focused checks and existing compatibility checks pass. No v0.4 Skill
  effectiveness evaluation is performed.
