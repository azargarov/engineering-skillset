# Engineering Skillset v0.3 — M00 Requirements and Scope Proposal

**Status:** Superseded by the Skill-based model delegation direction recorded
in [`../../ROADMAP.md`](../../ROADMAP.md). Retained unchanged as historical
proposal; its declarative routing and orchestration requirements are not the
active v0.3 scope.
**Baseline:** Published v0.2.1, as specified by the operator. The repository's
older `current.md` and v0.2 roadmap still describe the release candidate before
publication; this proposal does not revise that historical evidence.
**Authority:** [`../../VISION.md`](../../VISION.md), unchanged. This proposal
considers a runtime orchestration extension beyond the currently stated
product boundary and therefore requires explicit operator approval before
implementation.

## 1. Repository findings and constraints

The current product has four declarative presets (`prototype`,
`fast-development`, `performance`, `reliable`). Make composes selected Markdown
policy modules into standalone `dist/<preset>/AGENTS.md` and workflow Skills.
The presets share stable Skill names; `software-design` and `verification-qa`
have variants, while `implementation-review` and `project-handover` are shared.
`ess` installs or switches built artifacts and manages their ownership; it
does not compile modules or execute tasks. The user installer publishes
immutable local releases and switches a `current` link.

Core Policy preserves user-authorized scope, existing contracts, proportional
QA, evidence, and memory. The vision favors understandable Markdown, small
declarative configuration, deterministic builds, few commands, and explicitly
rejects unnecessary frameworks and lifecycle machinery. Existing module and
Skill contracts leave room for additional workflow guidance, but they do not
define executor configuration, task queues, a runtime protocol, credentials,
or isolation. Extending presets to select executors would conflate engineering
strategy with machine/provider availability; keep those concerns separate.

Architecture references inspected: [v0.2 architecture](../architecture/v0.2-architecture.md),
[module composition](../architecture/module-composition.md),
[module contract](../architecture/module-contract.md), and
[Skill contract](../architecture/skill-contract.md). Existing QA and handover
Skills establish review → final verification → acceptance reporting, and
require project memory to reflect actual progress. No existing ADR directory
or architecture decision record was found.

## 2. Proposed requirements

### Task selection and executor choice

- Classify each proposed unit by explicit user-approved scope, action class
  (analysis/review, documentation, code change, or verification), risk,
  required tools, and expected isolation. Classification may be supplied by
  the operator or recommended by a human-readable routing rule; it must not
  silently expand scope.
- Routing maps task classes and required capabilities to configured executor
  profiles, with a visible default and an explicit no-match outcome. An
  operator can manually choose or override the selected profile.
- Routing selects an execution mechanism, not a permission grant. Every run
  remains bounded by its task contract and the selected executor's enforced
  permissions.

### Provider and capability configuration

- Separate provider/model identity from executor/harness. A capability record
  must describe observed/declared support needed for selection: read/write
  access, shell, network, tool calling, structured output, cancellation,
  streaming, and isolation mechanism. Unknown capabilities are unsupported
  for routing until verified.
- Keep endpoint/model identifiers and non-secret configuration in an explicit
  user/project config. Credentials come from environment/credential stores;
  never place secrets in project memory, task manifests, or traces.
- Treat model capabilities as versioned operational facts, not provider-wide
  guarantees. A text API that can emit function-call JSON does not itself run
  tools or edit files.

### Task contract and controlled execution

Each run has a reviewable contract containing: task/input references; allowed
and excluded scope; expected artifacts/output; acceptance criteria and
required QA gates; selected executor profile; filesystem ownership; timeout
and resource limits. The executor must return a result and evidence mapped to
that contract. Missing/ambiguous acceptance criteria or unavailable required
capabilities stop or route to manual handling.

An executor must receive only the needed workspace. The default for an
executor that edits files is a disposable worktree or equivalent isolated
copy, owned by that run. It must not write concurrently into another executor's
workspace or the operator's active checkout. Integration of a result back to
the project is a separate, reviewable step. Read-only tasks may share a
snapshot. Filesystem and network permissions must be enforced by the runtime,
not merely described in the prompt.

### Parallel work and lifecycle

- Parallelize only independent tasks with disjoint write ownership, explicit
  dependency edges, and bounded concurrency. Require a human merge/review
  point before combining edits. If independence or ownership cannot be
  established, serialize.
- Bound wall-clock time, model/tool iterations, concurrency, input/output
  tokens when supported, and provider spend where measurable. Limits should
  be configured per run/profile with conservative defaults; unavailable
  accounting is reported as unavailable, not estimated as fact.
- Retry only classified transient failures, with a small configured cap and
  idempotent/replay-safe behavior. Never blindly retry a task after uncertain
  filesystem side effects. Cancellation must stop new work, terminate or
  signal the child process where possible, preserve partial output separately,
  and mark the run cancelled or incomplete.
- Fallback is explicit and capability-compatible. It must preserve contract,
  permissions, limits, and user-visible executor identity; never fall back to
  a broader-permission executor without approval.

### QA and memory

- Executors do not waive existing project QA gates. Their reports identify
  checks run, exact commands/results where available, and unrun checks.
  Required final verification is performed or confirmed independently of an
  executor's assertion where the task's acceptance criteria require it.
- Preserve run identity, task contract, executor/profile/model version,
  timestamps, status, retries/fallbacks, changed paths or patch digest,
  check evidence, and final disposition in a bounded trace/report. Redact
  secrets and avoid retaining full prompts/source by default; retention is a
  configuration decision.
- Project memory records meaningful decisions and milestone outcomes, not
  verbose agent traces. `current.md`, roadmap, milestone evidence, and decisions
  remain the project continuity source of truth; generated run reports may be
  referenced from them. Never mark executor output as verified or accepted
  without corresponding evidence or operator acceptance.

### v0.2.1 compatibility

- Preserve current preset names, compiled artifact layout, `ess` commands,
  install ownership/state format, and default installed behavior unless a
  future approved design proves a migration is necessary.
- Runtime routing is opt-in and independent of preset selection. Existing
  installations without routing configuration behave as they do on v0.2.1.
- Keep Skills standalone and the generated Core Policy portable. If v0.3
  adds guidance to policy/Skills, changes flow through existing composition
  and build paths; do not make installed guidance depend on a live source
  checkout or remote service.

## 3. Integration capability evidence

These observations are from official documentation reviewed on 2026-11-01;
they establish documented interfaces, not tested compatibility with this
repository or every model/version.

| Candidate | Confirmed capability | Not established / implication |
|---|---|---|
| Codex | Official material describes `codex exec` for bounded non-interactive jobs and a Codex harness with tools, sandbox/approval policy, and structured events. Self-hosted executor runs in a supplied environment. [Codex platform overview](https://developers.openai.com/blog/codex-as-a-platform) · [self-hosted sandboxes](https://developers.openai.com/api/docs/guides/agents-api/environments/self-hosted) | No repo-specific adapter, version pin, or integration test exists. CLI/harness authentication, exact lifecycle flags, and machine-specific sandbox strength must be qualified in a later milestone. |
| OpenCode | `opencode run` supports non-interactive scripted invocation; docs describe configurable providers/models and per-tool allow/deny/ask permissions, including filesystem external-directory controls. [CLI](https://dev.opencode.ai/docs/cli/) · [permissions](https://opencode.ai/docs/agents/) · [providers](https://opencode.ai/docs/providers/) | Execution safety still depends on effective config, host account, and runtime environment. Do not infer isolation from permissions alone; validate headless exit/result semantics and pin supported versions. |
| Ollama | Official API documents local and hosted endpoints and OpenAI-compatible interfaces. [API introduction](https://github.com/ollama/ollama/blob/main/docs/api/introduction.mdx) | API compatibility does not establish tool execution, agent loop, coding competence, model availability, or resource sufficiency. Treat as a model endpoint unless paired with a separately qualified harness. |
| Groq | Chat API documents function/tool-call requests and rate limits; docs explain the caller implements tool execution and the agent loop. [Tool use](https://console.groq.com/docs/tool-use/overview) · [API reference](https://console.groq.com/docs/api-reference) | Tool-call response is not autonomous repository access. Model-specific capability, provider limits, coding executor, and compatible harness remain to be qualified. |
| DeepSeek | Chat completion docs describe function tool calls; the guide explicitly has the caller execute tools and return results. [Tool calls](https://api-docs.deepseek.com/guides/tool_calls/) · [API](https://api-docs.deepseek.com/api/create-chat-completion/) | API tool calling alone is not a filesystem executor or safe agent. Mode/model-specific limitations and executor integration must be tested before routing work. |

Thus, for Groq, DeepSeek, or Ollama, a v0.3 executor would most likely be an
existing qualified harness (such as OpenCode) configured to use the model
endpoint; direct API function calling alone is insufficient. Compatibility
and capability claims must be verified by model/version, not inferred from
brand.

## 4. Minimal architecture options

Scores are qualitative: low complexity/burden and high reliability,
portability, and compatibility are desirable.

| Option | Complexity | Maintenance | Reliability | Portability | v0.2.1 fit |
|---|---|---|---|---|---|
| **A. Declarative routing, manually initiated** — small config maps task classes to named executor profiles; operator invokes installed CLI/tool and supervises execution. | Low | Low | High control, but manual steps and capability drift remain | High; shell/config plus existing tools | Highest; no runtime or installer change required |
| **B. Lightweight orchestrator + adapters** — validates contract, launches one configured executor process, collects status/report, enforces timeout/limits, optionally schedules independent tasks. | Medium | Medium/high; process, provider, errors, security, platform maintenance | Better repeatability; orchestrator becomes trusted control plane and failure surface | Medium; adapters and process semantics vary | Good if standalone opt-in CLI; installed defaults can remain unchanged |
| **C. Autonomous multi-agent orchestration** — runtime decomposes tasks, delegates dynamically, coordinates tools/agents and merges outcomes. | High | High | Hardest to bound, reproduce, debug, and verify | Low/medium; harness/provider-specific behavior | Lowest; expands product into runtime framework and threatens KISS/YAGNI |

**Recommendation:** Option A is the smallest adequate M00 recommendation and
the default MVP boundary. It covers configurable routing with operator control
without introducing a scheduler or executor abstraction prematurely. If
operator-approved acceptance requires enforced timeout/termination, repeatable
report capture, or isolation by the product itself, advance to a narrow form
of Option B: one local orchestrator invoking one qualified CLI adapter at a
time. Do not add task decomposition, dynamic delegation, agent swarms, or
automatic patch merging.

## 5. Recommended MVP boundary

For v0.3 MVP, propose:

- A small declarative config for task classes, executor profiles, declared
  capabilities, explicit routes, and conservative limits; no general plugin
  registry or model auto-discovery.
- Manual initiation and operator-visible executor selection/override.
- One qualified coding executor path and a documented text-only/model endpoint
  path only if it does not claim tool autonomy. Provider-specific routes are
  added only after capability and safety qualification.
- Contracted task execution against a disposable worktree with one writer per
  worktree; sequential execution by default. Parallel execution stays off
  until disjoint ownership and merge checks are proven.
- Run result with status, changed-path/patch digest, executor identity,
  acceptance mapping, and QA evidence. Preserve core v0.2.1 install and preset
  behavior; routing is optional.
- Explicit user/operator review before applying a patch to the primary tree.
  Existing QA gates and project memory remain authoritative.

Exclude from MVP: automatic task decomposition, dynamic agent spawning,
autonomous merges, model scoring/benchmark routing, broad provider catalogue,
remote distributed workers, auto-install/update, automatic retry after
uncertain side effects, and persistent conversation/task database.

## 6. Major risks and unresolved decisions

1. **Vision boundary:** v0.3 execution orchestration exceeds the current vision
   non-goal of avoiding custom frameworks. Operator must approve a narrow
   vision amendment or explicitly authorize a bounded experimental direction;
   do not silently revise `VISION.md`.
2. **Control boundary:** decide whether MVP means routing advice/manual launch
   (A) or requires the product to enforce timeout, filesystem isolation, and
   trace capture (B). This is the key architecture choice.
3. **Isolation semantics:** disposable worktree is a filesystem ownership
   boundary, not a security sandbox. Decide whether OS/container/network
   sandboxing is required and what platforms are supported.
4. **Acceptance responsibility:** decide which QA checks must be run by the
   orchestrator versus reported for operator execution, and whether final
   verification must use a different executor.
5. **Credentials and data handling:** choose supported secret source, telemetry
   and trace retention, source disclosure policy for hosted providers, and
   redaction behavior.
6. **Capability qualification:** select initial executor/model/version pair,
   supported operating systems, minimum checks for capability declarations,
   and policy for stale/unverified capability data.
7. **Budgets and recovery:** define user-configurable default wall/token/cost
   limits, what cost can be measured, retry classes, cancellation guarantees,
   and whether partial patches are retained.
8. **Config ownership:** decide whether routing is per-user or project-local,
   precedence rules, schema validation, and whether it belongs in this repo's
   installable product or a separate companion tool.

## 7. Suggested milestone breakdown

- **M00 — Requirements and scope:** this proposal; operator review and explicit
  approval of product boundary/options. No implementation.
- **M01 — Architecture decision and threat/failure model:** settle A vs B,
  contract/config shape, isolation, secrets, lifecycle semantics, compatibility
  invariants, and acceptance criteria; amend `VISION.md` only with approval.
- **M02 — Contract and routing prototype:** minimal schema/validator and
  deterministic route explanation; test missing capability, invalid scope,
  and no-match behavior without launching autonomous work.
- **M03 — One executor qualification:** disposable workspace integration for
  one pinned executor/version; establish permission behavior, status/result
  capture, cancellation, limits, and failure semantics. No parallel runs.
- **M04 — QA and project-memory integration:** preserve/collect gate evidence,
  produce trace/report, update continuity records from verified facts, and
  qualify compatibility with existing presets and installs.
- **M05 — Evaluation and release review:** compare representative task classes
  against manual v0.2.1 baseline, inspect reliability and operational cost,
  document limitations, then seek separate release authorization.

Milestones M01 onward are suggestions, not authorization to begin. Exit
criteria and evaluation thresholds require operator review.
