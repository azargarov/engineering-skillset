# Engineering Skillset v0.2 Architecture

**Status:** This document records the implemented modular architecture. The
broader v0.2 work was superseded by the v0.3.0 release, which is implemented,
verified, and owner-accepted; see the current [`ROADMAP.md`](../../ROADMAP.md).

## Product model

The governing product definition is [`../../VISION.md`](../../VISION.md).
Engineering Skillset provides task strategies through four initial presets:
`prototype`, `fast-development`, `performance`, and `reliable`.

- A **Module** is a small Markdown source component containing a particular
  engineering rule, behavior, or workflow variant.
- A **Preset** is a named configuration selecting explicit module files to
  produce a ready-to-use engineering strategy.
- A **Compiled Skill** is a complete, standalone `SKILL.md` generated from
  selected modules.
- The **Core Policy** is the universal engineering guarantees and instructions
  shared by all presets.

A declarative preset configuration selects files; Make orchestrates
deterministic compilation to stable per-preset directories and produces
standalone `AGENTS.md` and `SKILL.md` artifacts. Workflow Skill names remain
stable across presets while their content may differ. Core Policy remains
common and self-contained in generated project `AGENTS.md`, rather than being
copied wholesale into each Skill. The `ess` CLI installs or switches built
presets and links compiled Skills from the local user installation; it does
not compile source modules. The checkout-side installer publishes immutable
releases under the user data directory and switches the stable `current`
symlink. Preset switches govern subsequent work and do not
authorize retroactive refactoring. Existing project contracts and operational
requirements continue to apply. Git manages versions and updates. The design
should keep normal use to very few commands.

The first modular workflow was `verification-qa`; it now has strategy variants
for all four presets. `software-design` also has preset-specific modules.
`implementation-review` and `project-handover` remain shared because their
guidance does not currently need variants.

## Existing implementation and consistency review

### Reusable components

- `AGENTS.md` provides shared engineering guarantees and is the source for
  portable project policy composition.
- `modules/levels/` and `modules/priorities/` provide the policy sections
  selected by the four current presets.
- `scripts/compose-policy.sh` provides deterministic, validated Markdown
  composition for Core Policy, one level, and selected priorities; Make uses
  it to build each preset's standalone project policy.
- `Makefile` builds stable `dist/<preset>/` directories and standalone Skills
  from explicit selections. V2-04 stages and validates complete outputs, then
  publishes files by same-directory atomic rename while preserving preset and
  Skill directories used by existing links.
- `scripts/ess` installs, switches, checks, and uninstalls built presets. Its
  ownership state protects project policy and Skill links; `tests/ess.sh`
  covers those operations.

### Current supported behavior

- The active build supports exactly `prototype`, `fast-development`,
  `performance`, and `reliable`. Historical `personal` and `production`
  implementations are no longer in the active source tree; their records
  remain in Git history.
- Preset files select one policy level, priorities, and the shared four Skill
  names. Ordered Markdown selections compose the modular `software-design` and
  `verification-qa` content.
- The build stages and validates output before file-by-file publication.
  Successful rebuilds preserve active Skill links. An interruption during
  publication can leave mixed generations; `make clean` removes published
  outputs and leaves installed Skill links broken until a rebuild.
- `ess` copies `AGENTS.md` and links `skills/<name>` through the installed
  distribution's stable `current` path. The checkout CLI continues to use its
  local `dist/` for development.
  It lists and installs only the four supported presets, even if stale output
  directories remain in `dist/`.
- `ess uninstall` removes only paths verified against the ownership state. It
  leaves project Skill directories and central build artifacts in place.

### Retired implementation

- The active tree no longer includes the `personal` and `production` presets,
  or the superseded local installer and remote bootstrap. Their committed
  history remains available in Git.
- `scripts/compose-policy.sh` remains because the active Make build uses it;
  it is not a separate project installer.

### Resolved design constraints

- The four presets and stable `dist/<preset>/` build layout match `VISION.md`.
  Generated `AGENTS.md` is standalone; installed project Skill links require
  the user data directory but not the source checkout.
- Successful publication updates files in place so existing Skill links
  remain valid. A failed or interrupted multi-file publication may leave mixed
  generations; a successful rebuild restores the intended artifacts.
- Stale preset directories are not removed by publication because existing
  installations may link to them. `ess` does not advertise or install them.
- Installation and uninstall are multiple filesystem operations, not an
  atomic set. Ownership checks refuse modified managed files; concurrent
  changes during an operation are not qualified.

## Approved decisions and remaining review

The owner-approved decisions use explicit ordered Markdown module selections,
standalone artifacts under stable per-preset paths, file-by-file atomic
publication, and `ess` installation from built outputs. The existing managed
state, ownership checks, and refusal behavior remain in place. Automatic
policy backups and automatic Git updates are outside the v0.2 scope. See the
roadmap for the recorded V2-03 acceptance status and remaining release review.
