# v0.2 Architecture Decision

**Status:** Adopted for the V2-01 build stage

## Decision

- Markdown modules remain reusable source components. Keep their current
  locations under `AGENTS.md` and `modules/`; do not relocate them to a new
  `src/` tree in V2-01.
- A preset is a named build input whose output is a self-contained
  `AGENTS.md` plus individually usable Skills. For V2-01, define one Personal
  preset selecting the existing Personal level, both existing priorities, and
  all four production Skills.
- Reuse `scripts/compose-policy.sh` for policy composition. Its established
  fixed order is Core, level, priorities in identifier order, then optional
  modules. Skill artifacts remain separate from policy composition.
- Use Make as deterministic build orchestration. Copy standalone Skill source
  directories unchanged; no include language or template engine is needed.
- Treat `dist/` as generated output. `make clean` removes only that directory.
- Retain the existing installer and bootstrap as v0.1 historical tooling. The
  planned `ess` installer is deferred to a separately authorized milestone.

## Reconciliation with earlier architecture findings

The existing composition and Skill contracts distinguish standing policy from
workflow procedures, recommend fixed-order named sections, and require Core to
appear once and unchanged. This decision carries those findings into the
module/preset distinction: modules are source inputs, while a preset is the
built distribution unit. The supplied v0.2 roadmap further decides that built
policy is portable and Skills are standalone. V2-01 tests these structural
properties without claiming behavioral effectiveness or implementing the
future installation model.

## V2-01 composition

`personal` consists of Core Policy, Personal, Development Speed, Readability,
and the four Skills `software-design`, `implementation-review`,
`verification-qa`, and `project-handover`. The composer sorts priorities, so
its output order is deterministic regardless of selection order. The preset
configuration is intentionally small and declarative.

The root `ROADMAP.md` is a strategic index. The previous detailed roadmap is
preserved as `docs/development/roadmap-v0.1.md`; the supplied v0.2 plan is
preserved at `docs/development/roadmap-v0.2.md`.
