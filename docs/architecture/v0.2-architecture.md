# v0.2 Architecture — Proposed Reconciliation

**Status:** Proposed for owner review; supersedes the earlier V2-01-specific
architecture direction if accepted. This document records the clarified
product direction and its implications; it does not authorize implementation.

## Product model

The governing product definition is [`../../VISION.md`](../../VISION.md).
Engineering Skillset provides task strategies through four initial presets:
`prototype`, `fast-development`, `performance`, and `reliable`.

- A **Module** is a small Markdown source component containing a particular
  engineering rule, behavior, or workflow variant.
- A **Preset** is a named configuration selecting explicit module files to
  produce a ready-to-use engineering strategy.
- A **Compiled Skill** is a complete, standalone `SKILL.md` generated from
  selected modules.
- The **Core Policy** is the universal engineering guarantees and instructions
  shared by all presets.

A declarative preset configuration selects files; Make orchestrates
deterministic compilation to stable per-preset directories and produces
standalone `AGENTS.md` and `SKILL.md` artifacts. Workflow Skill names remain
stable across presets while their content may differ. Core Policy remains
common and self-contained in generated project `AGENTS.md`, rather than being
copied wholesale into each Skill. The `ess` CLI installs or switches built
presets and links compiled Skills from a central Git checkout; it does not
compile source modules. Preset switches govern subsequent work and do not
authorize retroactive refactoring. Existing project contracts and operational
requirements continue to apply. Git manages versions and updates. The design
should keep normal use to very few commands.

The first modular workflow experiment is `verification-qa`, with prototype
and reliable variants. Additional workflow variants should be introduced
where the presets require meaningfully different behavior.

## Existing implementation and consistency review

### Reusable components

- `AGENTS.md` already provides shared engineering guarantees and can remain the
  source for portable project policy composition.
- `modules/levels/prototype.md` contains some prototype-aligned guidance;
  inspect and selectively reuse its material rather than assuming the current
  level file fully expresses the new preset.
- `scripts/compose-policy.sh` provides deterministic, validated Markdown
  composition for Core Policy, one level, and selected priorities. Its
  validation and safe output behavior may inform a narrower preset composer.
- `Makefile` already builds stable `dist/<preset>/` directories and copies
  standalone Skills. Its `PRESET_*` model and unconditional removal of each
  destination during build need review against file-list configuration and
  publication requirements.
- Existing standalone Skills provide content to reuse. `verification-qa` is
  the initial candidate for splitting into explicit workflow variants.
- `scripts/ess` already resolves its central checkout and links built Skills;
  its install, status, and ownership checks are evidence for decisions about
  the revised target structure. `tests/ess.sh` records current behavior, but
  this documentation task does not change it.

### Behavior likely to change

- Preset configuration must select explicit module files, including workflow
  variants; current `presets/*.mk` files select one maturity level, two
  priorities, and the same four Skills.
- The product presets are prototype/fast-development/performance/reliable. The
  historical `personal` and `production` configurations and V2-01–V2-03
  evidence are preserved; they are not aliases for the new preset names.
- The current composer assembles project policy from a level and priorities;
  it does not compose modules into Skills. The build will need a simple
  declarative composition path for standalone Skills while keeping shared
  Core Policy in project guidance.
- The current Make build clears `dist/<preset>` and repopulates it. Since
  `ess` links Skills into these directories, cleaning or a failed rebuild may
  temporarily break active project links. Publication behavior needs
  qualification before the compiled layout is relied on centrally.
- `ess` currently discovers presets from `dist/`, copies `AGENTS.md`, and
  links `skills/<name>` from the preset directory. Its destination layout and
  managed-state rules may need adjustment once output structure is finalized.

### Work that may become obsolete

- The current `personal` and `production` configurations remain historical
  configurations; the four product presets will have their own explicit
  selections.
- A level-and-priority-only workflow may become unnecessary for the new
  preset build path. Existing modules and composer behavior should not be
  deleted until reuse and migration are reviewed.
- Existing v0.1 installer/bootstrap machinery may be simplified after the
  revised `ess` route is qualified. Preserve its released history and avoid
  unrelated archive changes.

### Potential conflicts with the clarified vision

- The earlier architecture calls Personal the first preset and defines
  prototype/personal/production. That differs from the four initial product
  strategies in `VISION.md`; retain the earlier configurations as historical
  evidence.
- The earlier source layout proposed flat Skill copies. This may still work
  for unchanged Skills, but modular variants need deterministic composition
  without runtime dependencies on source modules.
- V2-03 assumes all selected Skills live under `dist/<preset>/skills/`; the
  eventual stable per-preset layout must preserve or deliberately revise this
  contract.
- The desired central updates rely on linked Skill artifacts remaining
  available through rebuilds and updates. Current Make publication can break
  links while outputs are removed.
- The user vision requires portable generated project policy. Current `ess`
  copies built `AGENTS.md`, which supports portability if the build continues
  to emit a self-contained file.

## Decisions for owner review before coding

1. Agree on the smallest declarative format that names module files, including
   how a workflow selects a variant, without adding a template or dependency
   framework.
2. Set the final stable output path convention and required publication
   behavior while existing projects link to compiled Skills.
3. Review whether V2-03's managed-state, refusal, and switching behavior
   remains acceptable after the artifact layout changes.
4. Decide when obsolete v0.1 installation machinery may be simplified; keep
   v0.1 history, tags, and evaluation records intact.
